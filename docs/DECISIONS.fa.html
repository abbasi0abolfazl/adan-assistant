۱. نتیجه و حدود راستی‌آزمایی

برای این تسک، پروژه‌ای با نام «Nava Evidence Assistant» آماده شده است. راهکار شامل سه سند PDF، پایگاه داده رابطه‌ای با چهار جدول مرتبط، بازیابی معنایی مبتنی بر Embedding واقعی، تولید SQL توسط مدل، اجرای محدود و فقط‌خواندنی SQL، دو مؤلفه تخصصی مستقل، هماهنگ‌کننده، فراخوانی واقعی ابزار Calculator، API و فایل‌های Docker است.

۱۳۴ آزمون خودکار محلی با موفقیت اجرا شدند. استخراج PDF، پیش‌پردازش، اجرای SQLite، جلوگیری از دستورهای خطرناک، محاسبه اعشاری و منطق هماهنگ‌کننده بررسی شده‌اند. بخش ارتباط HTTP با مدل و پاسخ‌های مدل در آزمون‌ها، با جایگزین‌های آزمایشی صریح بررسی شده‌اند؛ بنابراین این عدد به معنای ۱۳۴ پاسخ صحیح از مدل واقعی نیست.

در محیط آماده‌سازی، کلید API و Docker در دسترس نبود و دسترسی شبکه کانتینر نیز با خطای DNS مواجه شد. به همین دلیل، اجرای زنده Embedding و LLM، کیفیت واقعی پاسخ فارسی و ساخت و اجرای Docker تأیید عملی نشده‌اند. اسکریپت جداگانه‌ای برای ثبت خروجی واقعی ده سناریو ارائه شده است. همچنین مخزن GitHub خودکار منتشر نشده است؛ طبق صورت‌مسئله، تحویل رسمی باید از طریق لینک مخزن قابل دسترس برای تیم ارزیابی انجام شود.

تفاوت این سه وضعیت مهم است: «پیاده‌سازی موجود است»، «منطق محلی آزموده شده است» و «مدل واقعی و Docker در محیط مقصد تأیید شده‌اند» یک ادعا نیستند.

۲. برداشت دقیق از صورت‌مسئله

صورت‌مسئله یک نمونه کوچک اما واقعی می‌خواهد، نه محصول کامل سازمانی. حداقل‌های آن RAG واقعی، تولید و اجرای SQL خواندنی، دو مؤلفه تخصصی، هماهنگ‌کننده، Calculator، API، Docker، مثال‌های قابل نمایش و مستندات قابل دفاع هستند. طراحی دامنه، انتخاب داده، مدل، کتابخانه و جزئیات معماری آزاد گذاشته شده‌اند.

بنابراین، فروشگاه فرضی، نام Nava، ساختار چهار جدول، مدل‌های پیش‌فرض، اندازه Chunk و سایر جزئیات زیر تصمیم‌های این پیاده‌سازی هستند؛ این موارد به متن تسک نسبت داده نمی‌شوند. رابط گرافیکی، احراز هویت، CI/CD و GPU عمداً اضافه نشده‌اند، زیرا الزام این تمرین نیستند و از زمان بررسی قابلیت‌های اصلی کم می‌کنند.

۳. انتخاب دامنه: فروشگاه فرضی تجهیزات دیجیتال

انتخاب: سیاست‌های مرجوعی، گارانتی و ارسال در اسناد؛ مشتری، محصول، سفارش و اقلام سفارش در دیتابیس.

دلیل: در یک دامنه واحد، سؤال توصیفی، سؤال عددی، فیلتر، Join، Aggregation و سؤال ترکیبی طبیعی داریم. برای مثال «شرایط مرجوعی چیست؟» سندی است، «فروش بهمنِ شمسی چقدر بود؟» به روشن‌سازی تقویم نیاز دارد، و «ذخیره موقت مرجوعی برای فروش فوریه ۲۰۲۶ چقدر است؟» سند، SQL و محاسبه را با هم لازم دارد.

مزیت: مسئله مصنوعیِ صرفاً ابزارمحور نیست؛ وابستگی واقعی بین سیاست کسب‌وکار و عدد دیتابیس نشان داده می‌شود. اطلاعات اشخاص یا مشتریان واقعی نیز وارد مخزن نمی‌شود.

عیب: تنوع داده محدود است و موفقیت روی این نمونه، کیفیت روی یک فروشگاه واقعی با سال‌ها داده را ثابت نمی‌کند. داده‌های ساختگی برای آزمون بازتولیدپذیر مناسب‌اند، نه برای ادعای دقت تجاری عمومی.

جایگزین: منابع انسانی یا پشتیبانی IT نیز مناسب بودند. فروشگاه به دلیل وجود طبیعی داده تراکنشی و محاسبات چندمرحله‌ای انتخاب شد.

۴. انتخاب Python، FastAPI و Pydantic

انتخاب: Python برای منطق برنامه، FastAPI برای API و Pydantic برای قراردادهای ورودی و خروجی.

دلیل: یک API کوچک، اعتبارسنجی روشن و تست‌پذیر لازم است. قراردادهای جداگانه برای Plan، پاسخ سندی، SQLDraft، آرگومان Calculator و پاسخ نهایی باعث می‌شوند خروجی مدل پیش از استفاده بررسی شود.

مزیت: مسیر سؤال تا پاسخ مشخص است؛ ورودی‌های ناقص یا ناسازگار رد می‌شوند؛ مستندات OpenAPI فراهم می‌شود؛ و مؤلفه‌ها در تست قابل جایگزینی‌اند.

عیب: اعتبارسنجی ساختار JSON به معنای صحت معنایی پاسخ نیست. مدل می‌تواند JSON معتبر اما SQL یا تفسیر نادرست تولید کند؛ به همین دلیل، کنترل‌های دیتابیس و شواهد جداگانه وجود دارند.

جایگزین: Flask یا PHP نیز می‌توانستند این تمرین را حل کنند. انتخاب Python به معنای نامناسب‌بودن PHP نیست؛ برای این پروژه مستقل، دسترسی یکپارچه به پردازش PDF، آرایه‌های عددی، قراردادهای داده و تست‌ها مناسب‌تر ارزیابی شد. پروژه فعلی به بازاربان یا سامانه‌های دیگر وابسته نیست.

۵. معماری یکپارچه ماژولار، نه Microservice

انتخاب: یک برنامه و یک کانتینر اجرایی با ماژول‌های مستقل برای API، عامل‌ها، بازیابی و ابزارها.

دلیل: استقلال مسئولیت‌ها لازم است، ولی استقلال شبکه‌ای هر مسئولیت برای این حجم کار لازم نیست. دو عامل تخصصی با کلاس و قرارداد جدا، بدون دو سرویس یا دو سرور هم مستقل هستند.

مزیت: راه‌اندازی و عیب‌یابی ساده‌تر است؛ خطاهای شبکه داخلی و مدیریت چند سرویس به تمرین اضافه نمی‌شوند؛ جریان اجرا در مصاحبه قابل دنبال‌کردن است.

عیب: عامل‌ها در سطح پردازش از یکدیگر جدا نیستند و مقیاس‌دهی مستقل ندارند. برای سامانه بزرگ یا چندمستاجری، این محدودیت باید دوباره ارزیابی شود.

معیار تغییر تصمیم: اگر اجرای طولانی، صف کاری، مقیاس مستقل یا مرز امنیتی پردازشی لازم شود، استخراج ابزارها یا عامل‌ها به سرویس مستقل قابل بررسی است.

۶. هماهنگ‌کننده محدود و صریح، نه حلقه آزاد Agent

انتخاب: مدل یک Plan ساخت‌یافته برمی‌گرداند. مسیرها documents، database، hybrid، calculator و clarify هستند. اجرای مسیر را کد کنترل می‌کند، نه یک حلقه نامحدود مدل.

دلیل: مسئله فقط چند قابلیت مشخص دارد. لازم است معلوم باشد چه زمانی سند، دیتابیس یا محاسبه اجرا شده و وابستگی مراحل چگونه رعایت شده است. مسیریابی با چند کلمه کلیدی ثابت جایگزین مدل نشده است.

مزیت: تعداد مراحل محدود، رفتار قابل ردیابی و خطاها قابل کنترل‌اند. در هر درخواست حداکثر یک بازیابی سندی، یک تولید SQL با حداکثر یک اصلاح، یک Calculator و یک جمع‌بندی نهایی وجود دارد. شکست امنیتی باعث افزایش مجوز نمی‌شود.

عیب: برای افزودن جریان‌های پیچیده جدید باید کد تغییر کند. LangGraph برای checkpoint، بازیابی اجرای نیمه‌تمام یا تأیید انسانی می‌تواند مناسب‌تر باشد، اما این نیازها در نمونه فعلی وجود ندارند.

دلیل استفاده‌نکردن از چند مدل متفاوت: تخصص عامل‌ها از مسئولیت، ورودی، Prompt و قراردادشان می‌آید؛ الزاماً به مدل‌های متفاوت نیاز ندارند. استفاده از یک Provider مشترک، تنظیمات و خطایابی را ساده می‌کند.

۷. انتخاب مدل تولید و روش اتصال

انتخاب: مقدار پیش‌فرض مدل تولید gpt-5.4-mini-2026-03-17 است و از متغیر محیطی قابل تغییر است. ارتباط با Responses API از طریق یک Adapter کوچک HTTP انجام می‌شود.

دلیل: خروجی ساخت‌یافته و Function Calling برای این مسئله لازم‌اند. انتخاب snapshot مشخص، تصمیم مدل را شفاف‌تر از یک نام مبهم می‌کند. استفاده از مدل میزبان‌شده نیز نیاز به GPU، بارگذاری وزن‌ها و سرویس‌دهی محلی را حذف می‌کند.

مزیت: تمرکز روی طراحی جریان، شواهد و ایمنی ابزارها باقی می‌ماند. قراردادهای HTTP در تست قابل بررسی‌اند و SDK بزرگ یا Framework عامل اضافی لازم نیست.

عیب: هزینه، اینترنت، دسترسی حساب به مدل و ارسال داده به Provider وجود دارد. همچنین نگهداری جزئیات قرارداد HTTP بر عهده پروژه است. این مدل در این محیط روی تسک benchmark نشده و «بهترین مدل» معرفی نمی‌شود.

جایگزین: SDK رسمی یا یک مدل محلی دارای Structured Output و Tool Calling معتبر. هر سرویس با برچسب OpenAI-compatible لزوماً کافی نیست؛ این پروژه به قرارداد Responses و Embeddings نیاز دارد، نه فقط Chat Completions.

۸. انتخاب Embedding و محل نگهداری بردارها

انتخاب: text-embedding-3-small با ۱۵۳۶ بُعد، جست‌وجوی دقیق شباهت کسینوسی با NumPy و نگهداری بردارها در فایل NPZ.

دلیل: فقط شش Chunk داریم؛ اضافه‌کردن سرویس Vector Database برای چنین حجمی ضرورت ندارد. ابتدا اسناد واقعاً به Embedding تبدیل می‌شوند و سؤال جدید نیز Embedding خودش را می‌گیرد. رتبه‌بندی از مقایسه بردارها حاصل می‌شود، نه از جدول سؤال و پاسخ ثابت.

مزیت: پیاده‌سازی و بررسی الگوریتم ساده است؛ برای هر راه‌اندازی دوباره هزینه نمایه‌سازی پرداخت نمی‌شود؛ سرویس اضافی وجود ندارد.

عیب: جست‌وجو با تعداد Chunkها رشد خطی دارد و نمایه در حافظه بارگذاری می‌شود. فیلتر دسترسی چندمستاجری، به‌روزرسانی پرتکرار و نمایه‌های بسیار بزرگ نیازمند طراحی قوی‌تر هستند. Embedding ابری نیز به API وابسته است.

جایگزین: برای مجموعه بزرگ‌تر FAISS، Qdrant یا pgvector؛ برای پردازش محلی یک Embedding چندزبانه مانند خانواده E5. این گزینه‌ها رد مطلق نشده‌اند؛ برای اندازه فعلی سربار بیشتری دارند.

۹. انتخاب PDFهای متنی انگلیسی و پیش‌پردازش

انتخاب: سه PDF متنی، هر کدام دو صفحه، با منبع JSON و اسکریپت بازتولید. اسناد انگلیسی‌اند و API سؤال فارسی و انگلیسی می‌پذیرد.

دلیل: تسک زبان اسناد را محدود نکرده است. هدف این نسخه، ارزیابی RAG است نه تبدیل تمرین به پروژه OCR یا حل همه مشکلات چیدمان PDF فارسی. یک سناریوی زنده فارسی برای ارزیابی ارتباط بین‌زبانی اضافه شده، ولی کیفیت آن هنوز اندازه‌گیری نشده است.

پیش‌پردازش واقعی: نرمال‌سازی Unicode، حذف علامت‌های جهت‌دهی مزاحم، یکسان‌سازی برخی حروف عربی/فارسی، اصلاح فاصله‌ها، اتصال شکست واژه در پایان خط و حذف سطرهای تکراری حاشیه صفحه. اعداد و بندهای سیاست حذف نمی‌شوند.

مزیت: سربرگ و پابرگ در بازیابی نقش کاذب نمی‌گیرند و صفحه واقعی منبع حفظ می‌شود. پردازش از PDF انجام می‌شود، نه از متن JSON به‌عنوان میان‌بُر زمان اجرا.

عیب: تشخیص حاشیه تکراری یک heuristic است و برای اسناد پیچیده نیاز به ارزیابی دارد. PDF اسکن‌شده، رمزگذاری‌شده یا فاقد متن با خطای روشن رد می‌شود؛ OCR پنهانی یا خروجی ساختگی وجود ندارد.

۱۰. انتخاب Chunking و Context

انتخاب: پنجره حداکثر ۱۸۰ کلمه با هم‌پوشانی ۳۰ کلمه و بدون عبور از مرز صفحه. هر صفحه نمونه فعلی در یک Chunk جا می‌گیرد. چهار نتیجه برتر با حد اولیه شباهت ۰٫۲۵ بررسی می‌شوند.

دلیل: اندازه محدود، Context را کنترل می‌کند و حفظ صفحه ارجاع را روشن نگه می‌دارد. هم‌پوشانی برای صفحه‌ای که چند Chunk می‌شود، احتمال قطع ارتباط جمله‌های مجاور را کمتر می‌کند.

مزیت: پیاده‌سازی قابل توضیح است و آزمون مشخص برای هم‌پوشانی و صفحه وجود دارد. شناسه منبع شامل سند، صفحه، شماره Chunk و بخشی از هش سند است.

عیب: کلمه با Token یکسان نیست. یک بند ممکن است بین دو صفحه تقسیم شود. عددهای ۱۸۰، ۳۰، ۴ و ۰٫۲۵ نقطه شروع‌اند، نه نتیجه بهینه‌سازی علمی این مجموعه.

نکته مهم: امتیاز کسینوسی ۰٫۲۵ احتمال ۲۵ درصد صحت نیست. باید با مجموعه ارزیابی شامل پرسش‌های قابل پاسخ و خارج از محدوده تنظیم شود. علاوه بر این فیلتر، عامل سندی کفایت شواهد را بررسی می‌کند.

۱۱. طراحی Cache و بازتولیدپذیری

انتخاب: اثرانگشت نمایه از محتوای سند، تنظیمات Chunking، نسخه پیش‌پردازش، مدل Embedding، تعداد ابعاد و آدرس Provider ساخته می‌شود. فایل نمایه بدون pickle بارگذاری می‌شود و ذخیره آن با جایگزینی فایل موقت انجام می‌شود.

دلیل: استفاده از بردارهای قدیمی پس از تغییر سند یا مدل، می‌تواند نتیجه نادرست اما ظاهراً عادی ایجاد کند.

مزیت: تغییر سیاست PDF باعث بازسازی خودکار نمایه می‌شود. تغییرات ناسازگار مدل یا ابعاد نیز قابل تشخیص‌اند. Cache خراب قابل بازسازی است؛ PDF همچنان منبع اصلی است.

عیب: این سازوکار برای یک پردازش اجرایی طراحی شده است و راهکار کامل ساخت هم‌زمان نمایه در چند Replica نیست. همچنین مدل Embedding بدون snapshot تاریخ‌دار می‌تواند در سمت Provider تغییر کند؛ بازتولید صددرصد بیتی همه پاسخ‌های ابری تضمین نمی‌شود.

۱۲. ارجاع، نقل‌قول و امتناع از پاسخ بی‌پشتوانه

انتخاب: عامل سندی باید کفایت شواهد، پاسخ، source_id و نقل‌قول دقیق برگرداند. مقدار عددی قابل استفاده در Calculator نیز باید در همان نقل‌قول وجود داشته باشد.

دلیل: صرف بازیابی یک متن مشابه یا درخواست «هالوسینیشن نداشته باش» کافی نیست. شناسه ناموجود، نقل‌قول ساختگی یا نرخ عددی فاقد پشتوانه باید در کد رد شود.

مزیت: صفحه و متن پشتیبان قابل بررسی‌اند. برای مثال نرخ «۵٪» باید با مقدار ۵ استخراج شود، نه ۰٫۰۵؛ تبدیل درصد وظیفه Calculator است و نباید پنهان شود.

عیب و مرز ادعا: وجود یک نقل‌قول واقعی، ثابت نمی‌کند همه جمله‌های پاسخ از آن نتیجه می‌شوند. مدل ممکن است نقل‌قول معتبر اما ناکافی انتخاب کند. این کنترل‌ها خطر را کاهش می‌دهند، ولی تضمین نبود هالوسینیشن یا صحت کامل معنایی نیستند. ارزیابی زنده و بررسی انسانی همچنان لازم است.

رفتار در کمبود داده: پاسخ وضعیت insufficient_evidence می‌گیرد. در سؤال مبهم، clarify انتخاب می‌شود. در مسیر ترکیبی، نبود سیاست لازم اجازه تولید عدد قطعی از فرضیات را نمی‌دهد.

۱۳. طراحی دیتابیس و قرارداد معنایی

انتخاب: SQLite با جداول customers، products، orders و order_items. رابطه‌ها شامل یک مشتری به چند سفارش، یک سفارش به چند قلم و هر قلم به یک محصول هستند.

دلیل: چهار جدول، حداقل دو جدول تسک را پوشش می‌دهد و Join معنادار ایجاد می‌کند. SQLite راه‌اندازی یک سرور دیتابیس مستقل را برای نمونه کوچک حذف می‌کند.

مزیت: داده‌ها از schema.sql و seed.sql قابل بازسازی‌اند؛ مبلغ فروش از قیمت تاریخی قلم سفارش به دست می‌آید، نه قیمت فعلی محصول. یک سفارش لغوشده، یک تخفیف خطی و یک سفارش ماه بعد برای سنجش خطاهای متداول وجود دارند.

عیب: SQLite نقش سروری و جداسازی چندمستاجری مشابه PostgreSQL ندارد. موجودی، هزینه کالا، مالیات، حمل و تراکنش بازپرداخت در مدل داده وجود ندارند. از این نمونه نباید سود واقعی یا مبلغ واقعی مرجوعی استخراج شود.

تصمیم راه‌اندازی: دیتابیس فقط بار اول ساخته می‌شود. دیتابیس موجود بی‌صدا پاک یا بازنویسی نمی‌شود؛ برای بازسازی باید ابتدا نسخه پشتیبان گرفت.

۱۴. پول، تخفیف، سفارش لغوشده و تقویم

انتخاب: مبلغ‌ها عدد صحیح ریال با واحد IRR هستند. تاریخ‌ها میلادی و ISO هستند. فروش برابر مجموع تعداد ضرب‌در قیمت واحد تاریخی، منهای تخفیف کل همان سطر، برای سفارش‌های completed است.

دلیل: بخش بزرگی از خطاهای NL2SQL از ابهام کسب‌وکار می‌آید، نه صرفاً Syntax. تخفیف کل سطر نباید دوباره در تعداد ضرب شود. سفارش cancelled به‌طور پیش‌فرض فروش محسوب نمی‌شود. شمارش سفارش پس از Join اقلام باید مراقب تکرار باشد.

مزیت: قرارداد قابل آزمون و اعداد مرجع روشن‌اند. تبدیل ریال به تومان یا ماه شمسی به ماه میلادی بی‌اجازه انجام نمی‌شود. نبود مقدار در SUM با عدد صفر یکی نیست.

عیب: این قرارداد عمداً ساده است. برای مالیات، مرجوعی واقعی، تقویم شمسی، ارز چندگانه یا سود، باید داده و منطق معتبر اضافه شود، نه فقط Prompt طولانی‌تر.

اعداد مرجع نمونه: فروش ژانویه ۲۰۲۶ برابر ۱۰۰٬۰۰۰٬۰۰۰ ریال و فوریه برابر ۱۲۵٬۰۰۰٬۰۰۰ ریال است. رشد ۲۵٪ و ذخیره موقت با نرخ سندی ۵٪ برابر ۶٬۲۵۰٬۰۰۰ ریال است. این اعداد با SQL و Calculator واقعاً بررسی شده‌اند، ولی خروجی زنده مدل محسوب نمی‌شوند.

۱۵. تولید واقعی SQL و یک اصلاح محدود

انتخاب: مدل، سؤال، Schema و قواعد معنایی را می‌گیرد و SQL جدید به‌همراه پارامترهای positional تولید می‌کند. هیچ نگاشت ثابت سؤال به SQL در مسیر اجرایی وجود ندارد.

دلیل: صورت‌مسئله صریحاً SQLهای Hard-code به‌جای تولید مدل را کافی نمی‌داند. قرارداشتن SQL ثابت در Seed، تست یا محاسبه مقدار مرجع با این ممنوعیت تفاوت دارد.

مزیت: پرسش‌های جدید می‌توانند Query متفاوت بسازند و SQL تولیدشده، SQL محدودشده اجرایی، پارامترها و نتیجه همگی قابل مشاهده‌اند.

عیب: Query می‌تواند از نظر نحو و امنیت درست اما از نظر معنای سؤال اشتباه باشد. قواعد معنایی و آزمون نتیجه برای کاهش این خطر هستند؛ کنترل امنیت، جایگزین سنجش صحت پاسخ نیست.

اصلاح: فقط یک تلاش اصلاح برای SQL نامعتبر مجاز است. تلاش دوم هم باید از همان مرز امنیتی عبور کند. دستور ممنوعه با مجوز بیشتر یا اتصال نوشتنی دوباره اجرا نمی‌شود.

۱۶. امنیت SQL: به‌جای اعتماد به Prompt یا Regex

انتخاب: اتصال mode=ro، فعال‌بودن query_only، غیرفعال‌بودن trusted_schema و بارگذاری Extension، استفاده از Authorizer با سیاست پیش‌فرض DENY، بررسی با کامپایلر خود SQLite و محدودیت منابع.

دلیل: شروع‌شدن Query با SELECT به معنای بی‌خطر بودن نیست. یک SELECT می‌تواند سراغ تابع نامناسب، اطلاعات Schema یا محاسبه بسیار سنگین برود. Parameter Binding نیز فقط جداسازی مقدار از ساختار Query است و ساختار تولیدشده مدل را به‌تنهایی امن نمی‌کند.

مزیت: تصمیم دسترسی در موتور دیتابیس اعمال می‌شود. فقط چهار جدول مجاز و مجموعه محدودی از توابع خواندنی قابل استفاده‌اند. DDL، DML، ATTACH، PRAGMA، توابع فایل و Extension، جداول داخلی و CTE بازگشتی رد می‌شوند.

چرا SQLGlot انتخاب نشد؟ این نسخه فقط یک Dialect دارد؛ کامپایلر SQLite همان ساختاری را بررسی می‌کند که واقعاً اجرا خواهد شد. SQLGlot برای تحلیل AST چند Dialect مفید است، اما الزام این تسک نیست و جایگزین مجوز اجرایی موتور هم نیست.

عیب: سیاست به SQLite وابسته است و Sandbox پردازشی مستقل وجود ندارد. امنیت میزبان و فایل دیتابیس خصمانه خارج از محدوده این دمو هستند. این معماری برای اتصال مستقیم به دیتابیس چندمستاجری واقعی بدون طراحی جدید کافی نیست.

۱۷. محدودیت تعداد ردیف و محدودیت کار موتور

انتخاب: پیش‌فرض خروجی ۱۰۰ ردیف است؛ یک ردیف اضافه برای تشخیص truncation خوانده می‌شود. SQL محدودیت زمان یک ثانیه، بودجه دستورهای ماشین مجازی و محدودیت طول Query، عمق عبارت، ستون، پارامتر و اندازه نتیجه دارد.

دلیل: LIMIT لزوماً هزینه Join یا Aggregation را کم نمی‌کند. ممکن است موتور میلیون‌ها ترکیب را پردازش کند و در آخر فقط یک ردیف COUNT برگرداند. بنابراین محدودیت خروجی و محدودیت مصرف پردازنده دو مسئله جدا هستند.

مزیت: نتیجه ناقص علامت‌گذاری می‌شود و برای محاسبه‌ای که نیاز به همه داده‌ها دارد، خروجی ناقص مبنای عدد قطعی قرار نمی‌گیرد. Query سنگین در تست واقعاً متوقف شده است.

عیب: حدود محافظه‌کارانه ممکن است Query صحیح اما پیچیده را نیز رد کنند. این اعداد برای نمونه کوچک تعیین شده‌اند و برای داده واقعی باید با اندازه داده و هدف تأخیر بازتنظیم شوند.

۱۸. Calculator واقعی و آرگومان‌های وابسته به شواهد

انتخاب: مدل یک Function Call واقعی با نام calculator می‌فرستد؛ برنامه آرگومان‌ها را اعتبارسنجی، ابزار را اجرا و function_call_output را با call_id متناظر به مدل برمی‌گرداند.

دلیل: نوشتن یک عبارت در پاسخ مدل یا اضافه‌کردن کلمه «Calculator» به Log، ابزار واقعی نیست. این تسک به اجرای تابع و استفاده از نتیجه آن در پاسخ نیاز دارد.

مزیت: عبارت، عملوندها، نتیجه و منشأ هر عملوند در خروجی مشخص‌اند. مبلغ از خانه نتیجه SQL و نرخ از نقل‌قول سند به متغیر نام‌دار تبدیل می‌شود. مدل حق ندارد عدد دلخواه را مستقیماً جای داده قرار دهد؛ تنها ثابت‌های عمومی صفر، یک و صد مجازند.

عیب: فراخوانی ابزار یک مرحله به هزینه و تأخیر می‌افزاید. الزام متغیرهای شواهدی ممکن است یک خروجی نامناسب مدل را رد کند. این انتخاب به نفع قابلیت توضیح و اعتمادپذیری است، نه آزادی حداکثری مدل.

مرز ادعا: منشأ معتبر عملوند و محاسبه درست، لزوماً فرمول درست برای نیت کاربر را ثابت نمی‌کند. سناریوهای رشد و ذخیره برای بررسی انتخاب فرمول نیز در ارزیابی آمده‌اند.

۱۹. چرا Decimal و AST محدود، نه eval؟

انتخاب: عبارت با AST خوانده می‌شود و فقط جمع، تفریق، ضرب، تقسیم، پرانتز و علامت مثبت/منفی مجاز است. محاسبه با Decimal و گردکردن صریح ROUND_HALF_UP انجام می‌شود.

دلیل: eval می‌تواند عبارت را به اجرای کد تبدیل کند. همچنین نمایش اعشاری پول و درصد باید از خطاهای رایج ممیز شناور دور بماند. نتیجه گرد‌شده و نتیجه پیش از گردکردن جدا ثبت می‌شوند.

مزیت: دسترسی به فایل، import، attribute، تابع، اندیس‌گذاری، توان و comprehension وجود ندارد. طول عبارت، تعداد گره‌های AST و بزرگی مقدار محدود است. تقسیم بر صفر خطای مشخص می‌دهد؛ رشد با مبنای صفر، به‌دروغ صفر درصد اعلام نمی‌شود.

عیب: ابزار عمداً ماشین‌حساب علمی عمومی نیست. درصد نمایشی معمولاً دو رقم اعشار و مبلغ ریالی بدون اعشار خروجی می‌گیرد. این قرارداد نمونه است؛ سیاست گردکردن واقعی هر سازمان باید صریح تعیین شود.

۲۰. API، خطا، زمان و گزارش مراحل

انتخاب: Endpoint اصلی POST /ask است. سؤال ۳ تا ۲۰۰۰ کاراکتر، بدنه حداکثر ۱۶ کیلوبایت، تعداد درخواست هم‌زمان محدود و زمان کلی درخواست کنترل می‌شود.

دلیل: خطای Provider، JSON نامعتبر، نبود سند، SQL نادرست یا تقسیم بر صفر نباید به traceback خام یا پاسخ موفقیت جعلی تبدیل شود.

مزیت: خطاها کد مشخص دارند و اسرار یا بدنه خطای Provider به کاربر نشت نمی‌کند. Trace هر درخواست نشان می‌دهد کدام عامل و ابزار اجرا شده‌اند. Log سرور فقط شناسه درخواست و نام مرحله را ثبت می‌کند، نه کل سؤال و داده‌ها.

عیب: خروجی API برای بررسی ارزیاب حاوی SQL و داده نمونه است؛ در محصول واقعی باید دسترسی به آن کنترل شود. همچنین retry فقط برای برخی خطاهای موقت و حداکثر یک بار انجام می‌شود؛ برای timeout خودکار تکرار نمی‌کنیم، چون ممکن است درخواست در سمت Provider پردازش و هزینه‌گذاری شده باشد.

۲۱. Docker و مدیریت وابستگی‌ها

انتخاب: Dockerfile با target اجرایی و target تست، Compose، کاربر non-root، پورت میزبان محدود به loopback، فایل‌سیستم ریشه فقط‌خواندنی و volume مجزا برای داده زمان اجرا.

دلیل: اجرای Docker الزام تسک است، اما نیازی به چند سرویس سنگین نیست. کلید API از تنظیمات محیطی گرفته می‌شود و در Git یا Image قرار نمی‌گیرد.

مزیت: مسیر اجرای مشخص و داده نمونه همراه پروژه وجود دارد. نسخه دقیق وابستگی‌های استفاده‌شده و وابستگی‌های فعال آن‌ها ثبت شده‌اند. تست‌های داخل کانتینر پس از ساخت Image به شبکه نیاز ندارند.

عیب و محدودیت: ساخت Image به دانلود اولیه نیاز دارد و در این محیط اجرا نشده است. هش فایل‌های نصب بسته‌ها و digest پیش‌فرض Image قفل نشده‌اند؛ بنابراین ادعای بازتولید کاملاً بیتی نداریم. برای سخت‌گیری بیشتر باید Image بررسی‌شده با digest ثابت و lock دارای هش انتخاب شود. متغیر PYTHON_IMAGE برای این کار پیش‌بینی شده است.

امنیت اسرار: .env راهکار ساده دمو است، نه جایگزین Secret Manager در تولید. همچنین store=false در درخواست مدل، به معنای تضمین حذف همه سازوکارهای نگهداری داده سمت Provider نیست.

۲۲. آزمون، مثال و تفاوت خروجی مرجع با خروجی واقعی مدل

انتخاب: تست‌های سریع بدون اعتبار API، همراه اسکریپت مستقل ارزیابی زنده.

دلیل: ایمنی SQL، جمع فروش، گردکردن، اعتبارسنجی ورودی و قرارداد Function Calling باید بدون وابستگی به رفتار متغیر مدل قابل تکرار باشند. از طرف دیگر، کیفیت واقعی مسیریابی، بازیابی و تولید پاسخ را نمی‌توان با Mock اثبات کرد.

مزیت: ۱۳۴ آزمون محلی عبور کرده‌اند. خروجی واقعی اجرای SQL و Calculator در deterministic-checks.json ثبت شده است. مثال‌های کامل API در reference_outputs.json صریحاً با عنوان پاسخ مدل آزمایشی علامت‌گذاری شده‌اند.

عیب: برای تحویل نهایی باید evaluate_live.py با پرچم --live اجرا شود، هزینه API پرداخت شود و پاسخ‌ها از نظر معنایی نیز بررسی شوند. عبور بررسی عدد و source_id به‌تنهایی همه جمله‌های پاسخ را تأیید نمی‌کند.

پوشش نمایش: دو پرسش RAG، سه پرسش SQL شامل فیلتر و Join و گروه‌بندی، رشد با Calculator، ذخیره ترکیبی سند/SQL/Calculator، سؤال خارج از محدوده، درخواست مخرب و یک پرسش فارسی در فایل سناریوها وجود دارند.

۲۳. دلیل حذف قابلیت‌های اضافی

UI، ثبت‌نام، احراز هویت، CI/CD، آپلود سند، OCR، جست‌وجوی وب، حافظه مکالمه، ابزار نوشتنی، مدیریت سفارش و استقرار GPU اضافه نشده‌اند.

دلیل: هیچ‌کدام جایگزین الزامات AI تسک نیستند. ابزارهای نوشتنی همچنین سطح خطر را افزایش می‌دهند. زمان باید روی صحت اعداد، امتناع درست، ارجاع، تولید SQL واقعی و توضیح‌پذیری صرف شود.

مزیت: راهکار متمرکز و قابل دفاع می‌ماند. عیب: محصول آماده ارائه عمومی نیست. اگر هدف از تمرین به سرویس واقعی تغییر کند، احراز هویت، مجوز دسترسی اسناد/ردیف‌ها، ثبت رخداد امنیتی، نسخه‌برداری و مدل حریم خصوصی باید دوباره طراحی شوند.

۲۴. انتشار GitHub و تحویل رسمی

انتخاب: پروژه به‌صورت پوشه آماده مخزن و ZIP انتقال داده می‌شود، اما انتشار خودکار عمومی انجام نشده است.

دلیل: حساب مقصد، نام مخزن، عمومی یا خصوصی بودن و دسترسی اعضای تیم ارزیابی مشخص نشده‌اند. انتشار بدون این تصمیم‌ها ممکن است کد یا اطلاعات آزمون را در مقصد ناخواسته قرار دهد.

مزیت: کنترل انتشار با صاحب حساب باقی می‌ماند. عیب: تا زمان ساخت مخزن و اعطای دسترسی، شرط روش تحویل رسمی تسک کامل نشده است. ZIP را نباید به‌عنوان جایگزین مورد پذیرش صورت‌مسئله معرفی کرد.

پیش از ارسال لینک: تست داخل Docker اجرا شود؛ خروجی زنده ده سناریو ثبت و بازبینی شود؛ .env و داده خصوصی وارد Commit نشوند؛ و دسترسی تیم به مخزن واقعاً بررسی شود.

۲۵. سناریوی اصلی برای دفاع در مصاحبه

پرسش نمونه: «طبق سیاست فروشگاه، ذخیره موقت مرجوعی فروش تکمیل‌شده فوریه ۲۰۲۶ چقدر است؟»

هماهنگ‌کننده مسیر hybrid را انتخاب می‌کند. عامل سندی سیاست ۵٪ را از صفحه دوم sales_handbook.pdf بازیابی و نقل‌قول آن را بررسی می‌کند. عامل دیتابیس Query تولید می‌کند و پس از کنترل فقط‌خواندنی، فروش ۱۲۵٬۰۰۰٬۰۰۰ ریال استخراج می‌شود. Calculator با متغیر مبلغ SQL و نرخ سند، عبارت revenue × rate ÷ 100 را اجرا می‌کند. خروجی ۶٬۲۵۰٬۰۰۰ ریال با برچسب «ذخیره موقت» برگردانده می‌شود، نه «مرجوعی واقعی».

در اجرای زنده، SQL و پاسخ مدل می‌توانند از نظر شکل متفاوت باشند؛ مقادیر مرجع و قواعد باید ثابت بمانند. در این محیط همین اعداد و عبور داده بین مراحل با جایگزین آزمایشی مدل و اجرای واقعی SQL/Calculator بررسی شده‌اند.

تمرین تغییر کوچک مناسب مصاحبه: نرخ سند را از ۵٪ به ۷٪ تغییر دهید، PDF را دوباره بسازید و سرویس را راه‌اندازی کنید. نمایه باید به‌دلیل تغییر هش بازسازی شود و ذخیره مرجع به ۸٬۷۵۰٬۰۰۰ ریال برسد؛ نیازی به Hard-code کردن نرخ جدید در عامل یا Calculator نیست.

جمع‌بندی

اصلی‌ترین تصمیم این راهکار، جداسازی سه موضوع است: مدل مسیر و ساختار پاسخ را پیشنهاد می‌کند؛ اسناد و دیتابیس واقعیت‌های قابل استناد را فراهم می‌کنند؛ و کد، مرز اجرای ابزار و محاسبه را کنترل می‌کند. هیچ‌کدام جای دیگری را نمی‌گیرد. کیفیت نهایی باید با خروجی زنده سنجیده شود، نه با تعداد Frameworkها، طول Prompt یا تعداد تست‌های Mock.

برای منابع رسمی APIها و کنترل‌های زیربنایی، بخش Primary technical references در DECISIONS.md را ببینید. برای تطبیق بندبه‌بند با فایل تسک، TASK_TRACEABILITY.md و برای وضعیت واقعی آزمون‌ها TEST_REPORT.md را مطالعه کنید.
